Executive summary

The server itself stayed up; only the Inventory API process died. Each outage started at the exact second the Linux kernel killed the API because it hit its configured memory ceiling (320 MiB), and ended when systemd restarted it about 45 seconds later, which is why it "came back by itself". The memory growth is driven by the scheduled job that calls the API's /report endpoint every 2 minutes: each call appears to leave roughly 110 MB allocated, so the third call after every restart pushed the service over its limit. The problem became visible at 06:58 UTC, when the service was reconfigured and restarted without access to swap; before that the same growth was silently pushed to swap (684 MB). A third, unreported outage occurred at 07:16 UTC, and at collection time (08:55 UTC) the API had been stopped manually and was not listening on port 8088.

Client report

Inventory API (HTTP port 8088, /health) intermittently unreachable on 2026-11-14; external monitor saw it down 07:04:03-07:04:48 UTC and 07:10:03-07:10:48 UTC; it recovered by itself. Ubuntu VM.

Root cause

inventory-api.service was killed by the cgroup OOM killer at both reported outage times (confirmed) because its memory grows by about 110 MB per /report request and, after a 06:58 reconfiguration removed swap from the unit (MemoryMax 320 MiB, swap limit 0), the third /report call after each start exceeded the limit (mechanism probable: inferred from timing and systemd accounting, app source and unit file not in the bundle).
  1. 06:41:47 inventory-api.service is started for the first time in the log window; from 06:42:01 a root cron job calls curl http://127.0.0.1:8088/report every 2 minutes.
  2. 06:41-06:58: each /report call leaves memory allocated; the unit hits its 320 MiB memory limit and the excess is pushed to swap (systemd: 320M memory peak, 684.3M swap peak after 9 calls, about 110 MB per call; sar shows pswpout 62-225/s in the same windows).
  3. 06:58:23 a daemon-reload plus restart of the unit is performed from an interactive session; from then on the kernel reports the cgroup with memory limit 327680 kB and swap limit 0 kB, so the overflow can no longer go to swap.
  4. The 1st and 2nd /report calls after a start fit under 320 MiB; the 3rd call (07:04:01, 07:10:01, 07:16:01) triggers an anonymous page fault in a worker thread that cannot be charged, and the memcg OOM killer kills python3 (anon-rss about 327 MB) within 0.1 s of the cron call.
  5. systemd marks the unit failed (result oom-kill) and restarts it after about 45 s (Restart= with a ~45 s RestartSec, inferred); the API is unreachable for exactly that gap, matching the monitor windows 07:04:03-07:04:48 and 07:10:03-07:10:48.

Trigger:Root cron job curl -s -m 60 http://127.0.0.1:8088/report every 2 minutes (even minutes); the 3rd call after each (re)start pushes the cgroup over its 320 MiB limit.
Why intermittent:The process restarts with a clean heap after each kill, so it takes 3 /report calls (about 6 minutes) to refill to the limit; this produces a regular 6-minute kill / 45-second outage cycle, which looks intermittent from the outside.
Why now:The service and the /report cron job first appear on 2026-11-14 at 06:41-06:42 (no trace in syslog.1). Until 06:58:23 swap hid the growth; the reconfiguration and restart at 06:58:23 removed the swap allowance (swap limit 0 kB in every OOM report afterwards), turning slow swapping into hard OOM kills.
To confirm:(1) systemctl cat inventory-api.service (and drop-ins) to confirm MemoryMax=320M, MemorySwapMax=0, Restart/RestartSec=45s and what changed at 06:58:23; (2) on a test instance, call /report 3 times and watch systemctl show -p MemoryCurrent inventory-api grow by about 110 MB per call; (3) app team review of the /report handler (tracemalloc) for objects/buffers retained after the response.

Contributing factors
  • Hard memory cap with no swap and no MemoryHigh soft limit: the first sign of pressure is a SIGKILL rather than throttling or an alert.
  • Restart delay of about 45 s defines the outage length; a shorter RestartSec would shrink each outage to a few seconds (but would not fix the leak).
  • No change record: unit changes at 06:41:47 and 06:58:23 were done via systemctl daemon-reload in interactive sessions without a load test of /report under the new limit.

F-2 · Memory retained per /report request (about 110 MB per call); 3rd call after each start hits the limit

high probable application · Phase 1: STAB-03

A root cron job calls /report every 2 minutes from 06:42:01. Every OOM kill happens about 0.1 s after the 3rd /report call since the last (re)start, and never after the 1st or 2nd. The killing allocation is an anonymous page fault in a short-lived worker thread (comm "Thread-NN (proc...", RIP in a memset-style rep stosb), consistent with a large buffer being allocated per request. Before swap was removed the unit reached 320M RAM + 684.3M swap after 9 calls (about 1004 MB / 9, about 110 MB per call). Mechanism inferred from timing and accounting; app source not available.
